# /rew_style

## 用途

写代码前先问清楚怎么做，再按用户选的方式执行。`refactor` 和 `extend` 是本技能里的两个分支，不需要另外加载技能。

## 开工前必须问清楚

开始分析代码、写实施计划或修改代码前，必须问用户下面三件事。可以一起问；用户在本次任务中已经明确回答的，不用再问。不能只凭任务描述猜用户的选择。用户没回答，就继续等，不能因为等了一段时间就当作同意，也不能提前做需要这些答案才能决定的工作。

1. **要不要测试？** 问清楚冒烟测试、回归测试，以及这次改动相关的单元测试、集成测试等，哪些要做、哪些不做。用户可以选不测试，也可以指定范围。按用户选择执行，最后说清楚哪些做了、哪些没做、哪些失败了；没做的不能说通过。
2. **走哪条路线？** 完全重构（`refactor`），还是增量扩展（`extend`）？完全重构只针对这次要改的部分，不是重写整个项目。确认后按对应分支做。
3. **谁来做决定？** 尽量让 Agent 自行决策，只有重大问题才问用户；还是无论问题大小，都先问用户、充分讨论后再做？后面的分析、计划和代码修改都按用户选的方式进行。

这些问题用于编码任务。只修改技能文档时，不需要问这三件事。

## 决策方式

- **Agent 决策**：遇到需要取舍的小问题，Agent 可以自行判断和决策，比如常规写法、命名和文件安排。遇到重大决策，比如改变需求、对外接口或已有业务，做不可逆的数据修改，或者在架构、性能和兼容性上做重要取舍，才向用户确认，并说清楚影响和推荐做法。
- **充分讨论（逐项讨论）**：无论问题大小，只要还没确定，都先和用户讨论，确认后再做。说清楚有哪些选项、有什么区别、推荐哪个。命名、代码放在哪个文件，以及接口、数据怎么流转、对象何时创建和释放、错误怎么处理、性能、兼容性和测试细节，也要确认。可以把相关问题一起问，但 Agent 提出的建议不能当作用户的决定。等回复时，只能继续做已经同意、而且不需要这些答案的工作。
- **新增类、文件和函数先问用户**：选择充分讨论时，新增类定义、代码文件或函数前，先说清楚为什么需要加、做什么、叫什么、放在哪里。新增函数还要说明参数、返回值和预期行为，得到用户明确确认后再加。私有辅助函数也要问。可以一次列出多个新增项，让用户逐项确认。已经确认的不用重复问；又要新增，或要改变职责、函数签名和位置时，再确认。
- 用户已经确认的决定继续有效，不用反复问。如果出现新冲突，或者需要改变原来的决定，再讨论。
- 计划模式也按用户选的决策方式来。先问清楚会影响方案的问题，再写计划；还没确认的地方标出来，不能提前开始实现。

## refactor 分支：完全重构

- 在这次确认的范围内，用新代码替换旧代码，把系统改得更简单。默认只用新实现。
- 尽量在同一轮完成新实现、删除被替代的旧函数、分支、适配层和配置，并更新项目内的调用代码。不要为了照顾旧调用而保留废弃 API 或包装函数。
- 不默认留下 fallback、兼容分支、同时跑的新旧两套实现，或只为过渡保留的代码。用户明确要求保留的兼容能力，要先写进方案，不能擅自删掉。
- 只给旧实现用的辅助函数、已经没用的代码、注释掉的旧代码，以及没人用的开关，也一起清理。删之前查清楚谁在用、有什么作用；拿不准能不能删时，按选定的决策方式处理。
- 不顺手改无关模块。按开工时确认的测试范围，检查替换后的功能。

## extend 分支：增量扩展

- 尽量保留旧业务代码和流程，只改新需求需要改的部分。
- 优先用现有的扩展点、接口和组件。能加代码接入，就不要把稳定的旧流程整条重写。
- 没有用户明确确认，不改变原来的返回格式、调用方式、数据格式和业务行为，也不删除旧函数或重写旧流程。
- 必须改多个地方共用的代码时，尽量局部修改，保持原有功能。新需求和旧业务有冲突，先说清楚，再和用户确认怎么处理。
- 不顺手重构、清理或重写无关代码。按确认的测试范围，检查新功能和直接受影响的旧功能。

## 代码写简单一点

- 能直接写清楚，就不要多加一层设计、抽象或模板。不要引入这次需求用不到的复杂结构。
- 短小、只用一次的逻辑留在原位置，不要为了形式统一拆成很多函数。只有逻辑很长，而且明确需要复用时，才单独提取函数。
- 不写冗长、绕弯的代码。新增的长代码要按功能分段，并用简短注释说明每段做什么。

## 命名要说清楚做什么

- 少用 `Ensure`、`Normalize` 这类含糊的词。`Ensure` 优先换成 `Check`、`Validate` 或具体动作；`Normalize` 只用于几何或图形学中的归一化，处理路径、文本、资源时，用能说清楚实际动作的名字。
- 自己定义的名称不要拿 `Resolve` 当万能动词。加载用 `Load`，获取已有对象用 `Get`，解析文本或序列化数据用 `Parse`，读取外部数据用 `Read`，转换用 `Convert` 或 `To`，查找用 `Find`。既获取又加载，可以用 `GetOrLoad`。
- 函数做了多件事，名字要说清楚主要做什么、产生什么结果。例如用 `LoadBuiltinShaders`，不要用 `ResolveBuiltinResources` 把实际动作藏起来。
- 不要什么都叫 `Make`。只有确实在构造新值时才考虑它；其他情况优先用 `Get`、`To`、`Build`、`Create`、`Write`、`Find`、`Check`、`Validate` 等具体动作。

## 注释怎么写

- 新增函数加一句简短中文，说明它做什么。C# 的 public 函数用单行 XML `summary` 注释。
- 长代码按功能分成几段，每段开头紧贴代码写一行 `//动作 + 对象`，说明下面这段做什么，不加句号、不编号。
- 代码块注释只说做什么，不展开解释为什么这样写、要注意什么或失败会怎样。不要用“为了”“避免”“确保”“否则”“以便”“防止”等说法。
- 只给有独立作用的代码块加注释，不逐行翻译代码。

```csharp
/// <summary>读取资源配置</summary>
public void ReadResourceConfig() {}

//绘制天空盒
if (camera.clearMode == ClearMode::SolidColor)
{
    RenderSkybox(scene, camera, gpuResourceManager);
}
```

## 完成后

按用户要求修改代码、给出 patch 或提供操作指导。简单说清楚选了哪个分支、改了什么、测试结果怎样。没做的测试如实说明；用户选了某种路线，也不代表可以顺手做任务范围以外的事。
