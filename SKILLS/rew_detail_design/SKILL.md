# /rew_detail_design

## 调用方式

本Skill**只能由用户显式调用**，禁止主动触发：

- 仅当用户自己输入 `/rew_detail_design`，或明确点名「用 rew_detail_design 生成详细设计」时才启用。
- 用户只是讨论需求、问方案、说「出个计划」「先设计一下」「写个技术方案」时，**不得**调用本Skill，按普通回答处理。
- 「当前任务看起来需要一份详细设计」不构成调用理由。是否要这份文档，决定权在用户。

## 核心要求

使用本Skill时**不修改、不落地任何代码**，只产出一份可直接开工的详细设计计划书：

- 新定义的类型、函数、对象的命名需要确定好，函数的实现也用文字描述出来。
- 足够详细，不含模糊或模棱两可的描述：任何水平的程序员或 AI Agent 拿到它，都不需要再怎么思考就能开始编码、落地，且实现出来的效果基本一致。
- 必要时可以包含少量伪代码。
- 使用者同时开着计划模式时，同样要产出这份详细设计，见「计划模式补充」。

## 用途

把「需求 → 方案 → 命名 → 类型 → 函数实现步骤 → 验证方式」一次性全部确定下来，产出一份详细设计计划书，交给后续实现者照着写代码。
详细计划书的读者是**执行者，不是设计者**：他不掌握本次对话的上下文，只会照文档写代码，不会也不应补做任何设计判断。


## 输出文档格式（强制）

产出的详细落地文档必须严格套用下面的骨架。章节标题、顺序、层级、进度标记一律照抄，不得自创章节、不得改写标题措辞、不得把 `#` 降级成 `##`/`###`、不得加编号或目录：

```
# 需求/目标
......

# 项目现状
......

# 总体路线图
- [x] XX系统落地
- [x] YY系统落地
- [ ] ZZ系统更新

# 关于XX系统
......

# 关于YY系统
......

# 关于ZZ系统
......

# 详细步骤
- [x] XX系统的aaaaa....
- [x] XX系统的bbbbb....
- [x] XX系统的ccccc....
- [x] YY系统的aaaaaa....
- [x] YY系统的bbbbbb....
- [x] YY系统的cccccc....
- [ ] ZZ系统的aaaaaa....
- [ ] ZZ系统的bbbbbb....
(需要足够细致)

```

各章节写什么：

- `# 需求/目标`：本次要达成的目标，以及可验收的判定标准。
- `# 项目现状`：与本次相关的现有实现，逐条给出 `文件路径:行号`，遵守「硬约束」的核实要求。
- `# 总体路线图`：每个系统一行；`- [x]` 表示现状已具备，`- [ ]` 表示本次要新增或更新。
- `# 关于XX系统`：每个系统一节，按「总体路线图」出现的顺序排列，标题里的 XX 换成真实系统名；写清该系统改什么、为什么这么改、牵涉哪些文件与类型。
- `# 详细步骤`：按系统分组，顺序与「总体路线图」一致；每步是一个 `- [x]` / `- [ ]` 列表项、单独成行，行内写清在哪个文件新增/替换/删除哪段代码、新符号的完整命名与签名；该步需要的字段列表、函数签名、伪代码接在这一行之下的缩进内容里。粒度要足够细，执行者不需要再做任何判断。

模板里的 `......` 和 `aaaaa....` 是占位符，实际文档中必须替换成真实内容，不得原样残留。本格式只约束排版骨架，「模糊写法黑名单」仍逐条生效。

复选框必须写成 `- [x]` 和 `- [ ]`：前缀的 `- ` 和方括号内的空格都不能省。裸写 `[x] XX系统落地` 或 `[] ZZ系统更新` 不会渲染成复选框（前者缺列表标记，后者括号内没有空白字符），只会原样显示成文字，属于静默失效。

## 实施阶段要打勾（强制）

「总体路线图」和「详细步骤」是活 Todo list，进入实施阶段后必须跟着进度勾选，不得只在结束时补勾：

- 每完成 `# 详细步骤` 里的一步，立刻把该行的 `- [ ]` 改成 `- [x]`。
- 某个系统在 `# 详细步骤` 里的条目全部勾完、且验证通过后，把 `# 总体路线图` 里该系统对应的 `- [ ]` 改成 `- [x]`。
- **只勾不改**：更新复选框是实施阶段唯一允许改动这份设计文档的地方。发现设计与现状不符、需要偏离设计时，先向用户求证，不得自行改写文档里的设计内容。
- 打勾改的是既有文档，不属于本Skill「禁止 Edit/Write」的范畴；但设计阶段本身不得建文档、不得勾选。

## 硬约束

- 禁止 Edit/Write 源码、工程文件、生成物，禁止构建、运行测试、执行 git 写操作。
- 详细计划书中每条「现状」都必须先核实（读过对应文件），引用既有符号时给出 `文件路径:行号`。无法核实的，写成疑问向用户求证，不得凭印象编写。
- 需求里没有、又无法由现状推导的决策属于用户所有：先问，不要替用户拍板

## 模糊写法黑名单

计划书中不能出现下列写法，必须改成确定表述：

- `等`、`等等`、`诸如……之类`
- 用于替代明确说明的 `类似`、`参考现有实现`（未指明文件与函数）
- `视情况`、`酌情`、`按需`、`适当`、`合理的`、`必要时`
- `可以考虑`、`建议`、`最好`、`尽量`、`原则上`
- `大概`、`若干`、`一些`、`多个`（未给出数量或判定条件）
- `TODO`、`TBD`、`待定`、`后续补充`、`具体实现略`
- `自行决定`、`自由发挥`、`按惯例`


## 计划模式补充

- 计划模式和本Skill不冲突，应该先生成Harness要求的普通计划，然后再生成本Skill要求的详细设计计划。  


## 与其他Skill的关系

本Skill只出设计，不落地。进入实现阶段后，按任务性质使用 rew_extend 或 rew_refactor，并遵守 rew_style 的代码风格；这些风格要点可提前写进计划书的禁止改动清单，减少实现阶段的偏差。

## 适用范围

用户要求「先出详细设计 / 先给实施计划」时使用。用户要求直接改代码时，不使用本Skill。
